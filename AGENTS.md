# Инструкции для ИИ: ИПС

Это учебная SaaS-платформа поддержки. Приоритет: быстрое рабочее ядро,
изолированные данные организаций, понятный код и экономный расход контекста.
Backend — **Python**, frontend — TypeScript. Решения: `docs/architecture.md`.

## Начало задачи

1. Прочитай свою карточку в `docs/plans/track-{a,b,c}.md` и локальный `AGENTS.md`.
   Краткая выдача: `python3 scripts/task_context.py <ID>`;
   `--contracts` добавляет только принадлежащие карточке API и используемые DTO.
2. Прочитай только связанные разделы `docs/contracts.md` и `docs/data-model.md`.
3. `contracts/openapi.json` — согласованный HTTP-контракт, а не доказательство
   готовности всех API. Актуальный статус задач смотри в GitHub Issues.
4. Выбери одну карточку, ветку `codex/<ID>-<short-name>` и одного владельца.
   Если GitHub недоступен, работай локально и точно сообщи, что не отправлено.
5. Первый запуск у другого участника: `docs/ai-setup.md`;
   перед выполнением плана — `docs/start-here.md`.

## Как выполнять

- По умолчанию одна кодовая модель со средним рассуждением: Terra medium
  либо сопоставимая доступная модель. Названия и уровни зависят от клиента.
- Одна задача за сессию. Если задача не помещается в 1–2 короткие сессии,
  раздели внутри карточки без смены контрактов. Не перепланируй весь проект.
- Не запускай агентов и несколько независимых ревью автоматически.
  Нужны явное поручение участника и полезная отдельная задача.
- Держись FastAPI + SQLAlchemy 2.x + Alembic + PostgreSQL;
  React + Vite + TypeScript. Зависимости Python через uv, frontend через npm.
- Не добавляй микросервисы, брокер, Kubernetes, автономные LLM-агенты,
  платёжную систему и отдельную векторную БД.
- Меняй только разрешённые пути карточки. Общие файлы — через указанных
  владельцев; правила описаны в `docs/team-workflow.md`.
- Сначала поведенческая проверка для бизнес-логики или исправления ошибки,
  затем минимальная реализация. Для документации и простого оформления
  достаточно соответствующей проверки; тесты ради тестов не нужны.
- Моки должны соблюдать настоящий контракт. `AI_PROVIDER=fake` допустим
  для разработки и CI, но интерфейс явно показывает демонстрационный режим.
- На общий API опирайся через порты и DTO; не импортируй ORM-модели соседнего
  домена в сервис. Связи metadata при сборке БД — оговорённое исключение.

## Обязательные инварианты

- `tenant_id` берётся из проверенной сессии/членства, а не из тела запроса.
  Каждый запрос, фоновая задача, вложение и поиск знаний ограничен tenant.
- Публичные ответы и поиск клиента никогда не содержат внутренних заметок,
  внутренних статей, приватных источников и сообщений помощника специалиста.
- Один активный ticket на conversation; назначение атомарное; роли проверяются
  сервером. После handoff ИИ не отвечает клиенту до явного возврата в bot.
- Документы и сообщения — недоверенные данные; модель не управляет доступами,
  SQL, сетью или состоянием заявки напрямую.
- Отказ ИИ не мешает создать ticket и написать человеку.
- Не коммить `.env`, ключи, токены, реальные переписки и личные данные.

## Проверки и завершение

Список команд и момент их появления: `docs/verification.md`.
Уже сейчас работают `python3 scripts/check_project.py` и
`python3 scripts/bootstrap_ai.py --check`.
Команды backend/frontend начнут работать после A01/B01; не выдавай их за
пройденные раньше. Для карточки проверяй затронутые тесты и типы, для PR — CI.

В ответе укажи результат, изменённые пути, фактически выполненные проверки,
ограничения и следующий ID. Не говори «готово», если проверки не запускались.
Если два разумных исправления не устранили проблему, сохрани краткий handoff
по `docs/prompts/task.md` и привлеки более сильную модель к конкретному вопросу.
Не выдавай недоступность плагина за запрет на локальную разработку.
