# Работа через GitHub

## Роли и права на файлы

Реальные логины и соответствие A/B/C хранятся в `docs/team.json`. Сейчас
Artiomion предложен как B; A/C пока не назначены. Это не три аккаунта одного
человека. У каждого свой clone, credentials и ветки.

| Пути | Основной владелец | Согласование |
|---|---|---|
| apps/, packages/, npm lock/workspace, frontend CI, tests/e2e | A | Reviewer B |
| backend core/platform/tickets, pyproject/uv.lock, infra, backend CI | B | Reviewer C |
| backend conversations/ai/knowledge, tests соответствующих доменов | C | Reviewer A |
| contracts | Владелец endpoint B/C | A + затронутый backend владелец |
| Alembic versions | Автор домена создаёт новый файл | B интегрирует heads |
| docs/plans/track-a,b,c | Соответствующий участник | Обновляет статус в своём PR |
| Общие инструкции, roadmap, team.json, tasks.json | B — интегратор | Все затронутые |

Общие файлы не редактировать одновременно. Для добавления зависимости C
пишет B точное имя и назначение; B делает маленький PR lock-файла либо
передаёт право на него на время одного PR. Python зависимости добавляются
через `uv add`, frontend — `npm install -w <workspace>` после A01.
Не держать эти PR до конца этапа: они нужны в начале зависимой карточки.

## Обычный цикл

1. Возьми Issues с ID своей карточки; перед стартом напиши владельца и статус
   в issue (сам человек или его ИИ по поручению). Не назначай чужую задачу себе
   без согласования. Шаблон issue задаёт output, тесты и разрешённые файлы.
2. Обнови main; создай `codex/A04-widget-history` или аналогичную ветку.
   Для первого commit подготовительного пакета main используется напрямую;
   дальше весь код идёт PR.
3. Одна короткая сессия модели — один проверяемый кусок. Не форматируй весь
   репозиторий и не меняй архитектуру ради карточки.
4. PR содержит ID, что теперь работает, фактические проверки, скриншот для UI
   и consumer impact для контрактов. `Closes #...` только при всей карточке.
5. Кольцо review: B смотрит A, C смотрит B, A смотрит C. Это проверка результата
   и тестов; глубокие изменения auth/tenant/AI приватности дополнительно смотрит
   затронутый участник. Review входит в баллы каждого.
6. CI зелёный, один peer approval; squash merge. Обновить свою ветку от main
   перед следующим PR. Чужую опубликованную ветку не force-push.

## Настройки репозитория

Владелец приглашает коллег; затем включает branch rule для main: PR,
1 approval, required checks после появления A01/B01, запрет force-push.
Возможность enforce rules зависит от тарифа GitHub/private repository;
если недоступна — те же правила соблюдаются командой вручную.
Не включать required check, которого ещё нет: это заблокирует первые PR.
Сейчас `planning-check` проверяет подготовительный пакет; это не CI приложения.

CODEOWNERS пока содержит комментарии, без выдуманных @логинов. После
заполнения team.json владелец переносит соответствия в `.github/CODEOWNERS`.
Автоматические авторы review не заменяют ручное назначение при пустых логинах.

## Равномерная нагрузка

После каждого M-этапа каждый сообщает фактическое время: implementation,
debugging, review/integration. Если один потратил >125% среднего, следующий
не начатый независимый кусок переносится на наименее загруженного участника;
обновляются карточка, team ownership для этого куска и tasks.json в одном PR.
Цель — примерно ±20% по сумме времени; баллы можно переоценить, не делать вид,
что 40 баллов математически гарантируют равные усилия.

Человек с готовой частью берёт чужое review, fixture или e2e сценарий из
следующего этапа. Он не начинает переписывать чужой домен. Интегратор B
не становится единственным тестировщиком: A владеет e2e, C — AI eval.

## Миграции и контракты

Правила — `docs/data-model.md` и `contracts/AGENTS.md`. Общий интерфейс
меняется до реализации. В конфликте generated типов всегда регенерировать
из объединённого OpenAPI. Миграции уже применённой БД не переписывать.
При двух heads B делает merge revision и проверяет чистый upgrade.

## Актуальность документов

GitHub Issues — оперативный статус; карточки — критерии приёмки;
OpenAPI — HTTP; architecture — решения. После изменения требований обновить
соответствующий источник и ссылки. Не записывать текущее состояние одной
карточки сразу в пять summary-файлов. Корневые task_plan/findings/progress
относятся только к подготовке репозитория, не к параллельной разработке.
